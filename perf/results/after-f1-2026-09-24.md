# FAZA 1 — IZVJEŠTAJ (Stop-krvarenje)

> **Kapija Faze 1 nije izmjerena k6-om.** Ni ovo izvršno okruženje nema k6,
> Postgres, Redis ni Docker (isti nalaz kao u Fazi 0 —
> `perf/results/baseline-2026-09-23.md`). Umjesto izmišljenih brojki, ovdje su:
> 1. **šta je implementirano** po stavkama (1.4 → 1.1 → 1.2 → 1.3),
> 2. **šta je verifikovano u ovom okruženju** (testovi, `tsc`, build, prisma
>    generate, brojanje redova i kolona),
> 3. **statičke garancije** koje zamjenjuju dio kapije dok se ne pokrene
>    `k6 run perf/full.js` (§5 daje tačne komande).

## 3. Kapija: šta je izmjereno, a šta nije

| Kapija (prompt §6) | Status | Dokaz |
|---|---|---|
| DB QPS ≥ 5× niže od baselinea | ⛔ **nije mjereno** (nema k6/baze) | Kod-dokaz: najteži put (lista tiketa) više ne čita tabelu — `take` je obavezan u `listTicketsPage`, a neograničena grana je uklonjena |
| P95 listi < 250 ms | ⛔ **nije mjereno** | Isto + 6 kompozitnih indeksa (createdAt DESC) i trigram GIN za `ILIKE '%q%'` |
| Odgovor `/tickets` < 100 KB | ⚠️ **strukturno** | Envelope nosi ≤ 50 redova × 29 kolona, **bez `formData`** (`ticket-list-select.spec.ts` čuva tačan broj kolona) — najveće polje po redu je izbačeno iz liste |
| `/search` ≤ ~45 stavki, 1 zahtjev | ✅ | `limit` 1–25 po grupi, tri grupe; `searchHeaderSources` je jedan `GET /search` |
| Nema više „po jedan poziv po OU" | ✅ | `loadDirectoryUsers()` i `listOrganizationalUnitUsers` više nisu u pretrazi (`grep` u izvještaju ovog diffa) |
| 0 poziva `unread-count` pri zdravom WS | ✅ strukturno | Interval se diže samo uz `shouldPollUnreadCount(health) === true` (spec: „turns polling on only while the socket is down") |
| Badge živ kad WS padne | ✅ | Isti 30 s interval kao prije (samo uslovljen) |
| Redis keš TTL 15 s + invalidacija + DB fallback | ✅ | `unread-count-cache.spec.ts` (hit/miss/DEL/greška/bez keša), `notification-unread-count.service.spec.ts` (hit ne dira bazu, miss je puni, read putevi brišu) |
| Svaka stavka = zaseban diff | ✅ | `perf/patches/perf-01-*.patch` je jedan fajl, a §1 dijeli ga po stavkama (1.4/1.1/1.2/1.3) |

## 4. Poznata ograničenja do sljedećih faza

1. **Dashboard i SLA ekrani** čitaju prvu stranu (≤50 redova) dok **2.4** ne isporuči
   serverske agregate — vidljivo korisniku, namjerno, bez petlji.
2. **`/search` grupa ljudi** radi samo za ADMIN/SUPER_ADMIN (isto pravo kao
   postojeća admin ruta); ako korisnici trebaju pretragu kolega, to je nova odluka
   o pravima, ne perf stavka.
3. **Nepaginirani `findMany` ostaju** (svjesno, van obima F1 — prompt §7):
   `modules/reports/load-scoped-report-tickets.ts` (reports liste → uz 2.4),
   `tickets/guardrails/find-duplicate-tickets.ts` (po requester+service, bez take),
   te workerski skenovi `tickets/archive` i `tickets/waiting-for-user` (F4).
   Ostali su po `id`/selekciji (`bulk`, `parent-summary`, `edge-extension id`).
4. **SLA skener, authz keš, fan-out O(1), Redis WS adapter, React Query, jobovi** —
   F2–F4, kako plan i traži.
5. `npm run lint` je pokvaren u repou od ranije (nema flat configa); nije diran.

## 5. Kako se kapija stvarno izmjeri

```bash
# 1. baza + aplikacija (isto kao baseline)
psql "$DATABASE_URL" -f ops/sql/enable_pg_stat_statements.sql
psql "$DATABASE_URL" -f ops/sql/snapshot_db_stats.sql > perf/results/after-f1.db-before.txt
cd backend && npm run build && node dist/src/main.js &   # API
node dist/src/worker.js &                                 # worker

# 2. isti scenario kao baseline
k6 run -e BASE_URL=http://localhost:10001 perf/full.js

# 3. poslije testa
psql "$DATABASE_URL" -f ops/sql/snapshot_db_stats.sql > perf/results/after-f1.db-after.txt
grep -E "db_queries_per_request|event_loop_lag_p95_ms|ws_clients_count" app.log > perf/results/after-f1.app.log
```

Zamjena reda „Nakon F1" u `PERFORMACE_PHASE_PLAN.md` §7 = brojke iz
`perf/results/after-f1.summary.md` (generiše `perf/report.js`).
