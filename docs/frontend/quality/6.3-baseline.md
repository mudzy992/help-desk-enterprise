## Critical API boundary baseline

Aktuelni katalog sadrži osam runtime-validiranih granica:

1. session/capabilities;
2. authentication session;
3. install readiness;
4. paginated ticket envelope;
5. config package preview;
6. routing coverage;
7. service catalog batch;
8. admin settings registry.

Postojeći contract guard potvrđuje da odgovarajući service koristi `apiRequestValidated` i imenovani parser. Faza 1 dodaje stvarni shared response fixture, pozitivni fixture i negativni ugovor; Faza 0 samo zaključava polazni katalog.

## Route i test evidence baseline

- Router koristi lazy page module i root route error boundary.
- Permission-sensitive rute su centralizovane kroz `protectedRoutes` katalog.
- Direktni page test nije uniforman za svih 47 page modula.
- Domenski dokaz je raspoređen između page, component, hook/lib i E2E nivoa.
- Faza 5 uvodi route evidence registry bez trivijalnog dupliciranja testova.

## Cache, realtime i recovery baseline

Aktuelna zaštita uključuje:

- centralne React Query key fabrike;
- session-aware cache reset;
- visibility-aware polling;
- realtime invalidation;
- partial-resource error modele;
- operation/race guardove;
- module-size, i18n, semantics i critical-boundary testove.

Faza 0 ne uvodi novi paralelni cache ili polling framework.

## Regresijska pravila za naredne faze

1. Machine-readable baseline i izvršni module guard ostaju sinhronizovani.
2. Nijedan novi application modul ne dobija legacy izuzetak bez posebnog nalaza i ownera.
3. Smanjeni hotspot ceiling ne vraća se naviše.
4. Novi runtime-validirani API boundary mora ući u critical boundary katalog i Faza 1 fixture registry.
5. Novi route mora imati capability odluku i evidence registry stavku.
6. Novi user-facing tekst mora proći bs/en parity.
7. Novi chart ili wide table mora imati semantic/scroll-region ugovor.
8. Produkcijski dependency audit mora ostati čist.
9. Bundle budget se ne povećava bez eksplicitnog obrazloženja.
10. OPEN-CI-FINAL se i dalje vodi samo u planu 6.3 §1.2.
