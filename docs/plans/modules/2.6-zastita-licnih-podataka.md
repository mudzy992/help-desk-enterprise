# 2.6 Zaštita ličnih podataka (ZZLP BiH): detaljni dizajn

> Status: **✅ završeno i verifikovano na stagingu** (2026-09-28). §16 odobren u cijelosti; zaključak u §17.
> Fazni plan: `docs/plans/05-FAZNI-PLAN-NADOGRADNJE-2026.md` §2.6.
> Napomena: dokument je tehnički dizajn, ne pravno mišljenje. Rokove čuvanja i pravne osnove
> potvrđuje službenik za zaštitu ličnih podataka (DPO) institucije. Sistem daje alate i zadane
> vrijednosti; odluke o konkretnim rokovima ostaju u postavkama.

## 1. Cilj

Help-desk obrađuje lične podatke zaposlenih: ime, e-mail, OJ, AD atribute, IP adrese sesija i
slobodni tekst tiketa. Paket treba omogućiti:

1. **Prava nosilaca podataka** (ZZLP BiH čl. 17–24), uz **rok od 30 dana**, produživ za još
   60 dana uz obrazloženje (čl. 14):
   - evidenciju zahtjeva;
   - izvoz podataka (pristup i prenosivost);
   - anonimizaciju (brisanje) bivšeg zaposlenika.
2. **Anonimizaciju bivšeg zaposlenika.** Ime i e-mail zamjenjuju se pseudonimom u tiketima,
   porukama, notifikacijama i auditu, a **hash lanac audita ostaje provjerljiv**.
3. **Politike zadržavanja** (načelo ograničenja roka čuvanja) za priloge, sadržaj poruka,
   audit, sesije i ulazne e-mailove. Svako čišćenje daje **izvještaj šta je obrisano**.
4. **Evidenciju aktivnosti obrade** i **obavještenje o obradi** (čl. 15) kao generisani
   dokument i stranicu. Tako institucija ima dokaz „integrisane zaštite” (čl. 26).

Izvan obuhvata:
- prijava povrede Agenciji u roku od 72 h (čl. 35) je organizacioni proces; dat će se samo
  runbook;
- šifrovanje baze u mirovanju (infrastruktura);
- pravni tekstovi (unosi ih institucija).

## 3. Zatečeno stanje (nalazi iz koda)

### 3.1 Šta postoji
- Postavke `private.ticket.attachments.retentionDays` (365), `private.observability.auditRetentionDays` (90)
  i `private.observability.requestLogRetentionDays` (14).
- Radni zadaci za zadržavanje: notifikacije (90 d), ulazni `.eml` (`rawRetentionDays`), DLQ integracija,
  memorijski request log.
- Audit s hash lancem (`AuditLog.previousHash/hash`), verifikacija od genesis zapisa
  (`verify-audit-log-chain.ts`), izvoz CSV/JSON.
- Brisanje korisnika (`DELETE /users/:id`) i deaktivacija; AD sync postavlja `directoryDeactivatedAt`.
- Redakcija osjetljivog sadržaja pri unosu (1.x `assert-ticket-content-redaction`).

### 3.2 Nalazi (bitni za usklađenost)
1. **N1: „mrtve” postavke.** `attachments.retentionDays` se parsira, ali **nijedan posao ne briše
   priloge**. `observability.auditRetentionDays` se samo ispisuje u support bundle, **audit se nikad
   ne čisti**. Postavke obećavaju nešto što sistem ne radi; to je rizik pri inspekciji.
2. **N2: lanac se ne može skratiti.** Verifikacija uvijek kreće od genesis zapisa. Bilo kakvo
   brisanje ili izmjena starog zapisa (retencija, anonimizacija) danas daje „lanac narušen”.
3. **N3: hash pokriva metapodatke doslovno.** Svaka izmjena `metadata` (npr. e-mail u zapisu
   neuspjele prijave) ruši lanac.
4. **N4: brisanje korisnika nije anonimizacija.** `Ticket.requester` je `onDelete: Restrict`, pa
   korisnik s tiketima ne može biti obrisan. Oni bez tiketa se brišu fizički, uz `SetNull` na
   porukama i auditu, pa se gubi „ko je šta uradio” bez pseudonima.
5. **N5: denormalizovani lični podaci** van tabele `User` (inventar u §6.2): naslov i tijelo
   notifikacija, `NotificationEmailDelivery.toAddress`, `InboundEmail.fromAddress`,
   `UserSession.ipAddress/userAgent`, `ManualDirectoryUser`, slobodni tekst tiketa i poruka
   (potpisi, spominjanja).
6. **N6: nema traga zahtjeva nosilaca.** Rokovi od 30 dana se danas prate van sistema.

## 4. Registar zahtjeva nosilaca podataka (R)

### 4.1 Model

```prisma
model DataSubjectRequest {
  id              String   @id @default(cuid())
  /// ACCESS | PORTABILITY | ERASURE | RECTIFICATION | RESTRICTION | OBJECTION
  type            String   @db.VarChar(24)
  /// RECEIVED | IN_PROGRESS | EXTENDED | COMPLETED | REJECTED
  status          String   @db.VarChar(16)
  subjectUserId   String?            // null ako je lice već anonimizovano/nepoznato
  subjectLabel    String   @db.VarChar(200) // kako je zahtjev zaveden (bez pseudonimizacije do izvršenja)
  channel         String   @db.VarChar(16)  // EMAIL | PAPER | PORTAL | IN_PERSON
  receivedAt      DateTime
  dueAt           DateTime            // receivedAt + 30 d
  extendedDueAt   DateTime?           // + 60 d, samo uz extensionReason
  extensionReason String?  @db.VarChar(1000)
  rejectionReason String?  @db.VarChar(1000)  // čl. 14(4): razlozi + pouka o prigovoru
  handlerUserId   String?
  notes           String?  @db.VarChar(4000)
  resultRef       String?  @db.VarChar(300)   // id izvoza / anonimizacije
  createdByUserId String?
  createdAt       DateTime @default(now())
  updatedAt       DateTime @updatedAt
  @@index([status, dueAt])
  @@index([subjectUserId])
}
```

### 4.2 Ponašanje
- Rok se računa automatski. Produženje je jednokratno, traži obrazloženje i dozvoljeno je samo prije
  isteka prvih 30 dana (čl. 14(3)).
- **Podsjetnik** 7 dana i 1 dan prije roka ide e-mailom i in-app obrađivaču i nosiocima
  `privacy.manage`. Na stranici je crveni brojač zakašnjelih zahtjeva.
- Odbijanje traži obrazloženje. Sistem nudi tekst pouke o pravu na prigovor Agenciji (uređuje se u
  postavkama).
- Svaka promjena ide u audit (`privacy.request.*`). Zahtjev se nikad ne briše; na njega se
  primjenjuje posebna retencija registra (zadano 5 godina, §9).
- Izvoz i anonimizacija se mogu pokrenuti iz zahtjeva. Rezultat se automatski veže (`resultRef`),
  a zahtjev prelazi u COMPLETED.

## 5. Izvoz podataka korisnika (pristup i prenosivost) (E)

### 5.1 Sadržaj paketa (ZIP)
| Fajl | Sadržaj |
|---|---|
| `README.txt` (bs/en) | Šta paket sadrži, datum, ko je izvezao, šta je izostavljeno i zašto |
| `profile.json` | Profil, OJ, uloge, grupe, preferencije (jezik, notifikacije), MFA status (bez tajni) |
| `tickets.json` + `tickets.csv` | Tiketi gdje je podnosilac: metapodaci, opis, forme, status, CSAT |
| `messages.json` | Javne poruke na tim tiketima (autor imenom samo ako je autor subjekt, ostali kao uloga: „Agent”, „Korisnik”) |
| `authored.json` | Poruke i interne bilješke koje je **subjekt napisao** (i agent je nosilac podataka) |
| `activity.json` | Njegove radnje na tiketima, evidencija vremena (1.3), spominjanja |
| `sessions.json` | Sesije zadnjih N dana: vrijeme, IP, user agent |
| `notifications.json` | Notifikacije u retencionom prozoru |
| `audit.json` | Audit zapisi gdje je subjekt akter ili entitet |
| `attachments/` | Prilozi koje je subjekt **sam priložio** (opciono, zadano uključeno, limit 500 MB) |

- Format je JSON (mašinski čitljiv, prenosivost), CSV za tabelarne podatke (UTF-8 s BOM), ključevi
  su na engleskom, a README na bs/en.
- **Zaštita prava drugih:** tuđe interne bilješke o subjektu **se zadano ne uključuju**. Admin ih
  može uključiti pojedinačno uz obrazloženje, koje ide u audit. Imena drugih zaposlenih u porukama
  ostaju kako su napisana, jer su dio komunikacije koju je subjekt već vidio.
- Generiše se asinhrono (BullMQ `privacy-export`), fajl se čuva u storage-u **šifrovan
  (AES-256-GCM, ključ po izvozu)**. Link za preuzimanje važi 7 dana, preuzimanje traži ponovni MFA,
  broj preuzimanja se evidentira, a nakon isteka fajl se briše.
- Preuzima samo osoba koja je pokrenula izvoz (DPO ili admin), koja ga predaje nosiocu. Nosilac ne
  preuzima sam (portal za samousluživanje nije u obuhvatu, §16 pit. 5).

### 5.2 Performanse
Upiti idu po `requesterId`, `authorUserId` i `actorUserId` (indeksi postoje) u serijama od 1000,
strimovanjem u ZIP. Cilj: korisnik s 5000 tiketa za < 60 s na stagingu.

### 5.3 Implementacijske odluke (korak 5)
Kod: `backend/src/modules/privacy/export/`.

- **Šifrovanje.** Paket se čuva kao `<uploads>/privacy-exports/<id>.hdx`, u segmentiranom
  AES-256-GCM formatu:
  - segmenti su od 1 MiB, svaki s vlastitim tagom;
  - nonce se gradi kao `baza || brojač`, a zadnji segment je označen u AAD-u. Zato se otkrivaju
    izmjena, skraćivanje i promjena redoslijeda, i to prije nego što se ijedan bajt pošalje.

  Ključ po izvozu je nasumičan. Umotava se glavnim ključem (`PRIVACY_EXPORT_KEY`, ili HKDF iz
  `MFA_ENCRYPTION_KEY`) i čuva se u zaglavlju fajla, pa u bazi nema ključeva. Ako nema ni jednog od
  ta dva ključa, izvoz se odbija.
- **Preuzimanje.** Ide preko `POST /privacy/exports/:id/download` s MFA kodom u tijelu (ili svježom
  sesijom za SSO naloge).
  - Dozvoljeno je samo osobi koja je pokrenula izvoz, dok link ne istekne (`linkValidDays`, zadano 7).
  - Svako preuzimanje povećava `downloadCount` i upisuje audit zapis `privacy.export.downloaded`.
  - Dešifrovanje ide „u letu", bez privremenog nešifrovanog fajla.
- **Istek.** Održavanje (svakih 15 min) briše fajl i postavlja status EXPIRED. Nastavlja i poslove
  zaboravljene u statusu QUEUED te preuzima zastarjele poslove u statusu RUNNING.
- **Sadržaj.** Paket sadrži fajlove iz §5.1.
  - U `messages.json` drugi autori su prikazani ulogom („Agent", „User", „System").
  - Tuđe interne bilješke ulaze samo uz `includeInternalNotes` i obrazloženje od najmanje 10 znakova,
    koje ide u audit zapis `privacy.export.requested`.
  - Za priloge vrijedi limit `maxAttachmentMb`. Preskočeni prilozi su navedeni u
    `attachments/skipped.json`, a imena fajlova se normalizuju.
  - CSV je u UTF-8 s BOM-om, s `;` kao separatorom, a formule se neutralizuju (`'=`).
- **Jedan aktivan izvoz po osobi** (QUEUED ili RUNNING). Dok je izvoz aktivan, anonimizacija je
  blokirana.
- **Performanse (§5.2).** Upiti idu keyset paginacijom (`id > cursor`) u serijama od 1000.
  Lokalno, 5001 tiket i 20 002 poruke izvezu se za 1,9 s. Test je opcioni
  (`PRIVACY_IT_PERF=1`); cilj na stagingu je < 60 s.
- **Ključ.** Promjena `PRIVACY_EXPORT_KEY` čini postojeće READY pakete nečitljivim. Rješenje je
  pokrenuti novi izvoz.

## 6. Anonimizacija bivšeg zaposlenika (A)

### 6.1 Preduslovi i tok
1. Kandidati su korisnici s `isActive = false`, deaktivirani prije ≥ N dana
   (`privacy.anonymization.candidateAfterDays`, zadano 180) i bez pravne blokade. Lista je na
   stranici „Privatnost → Anonimizacija”.
2. **Blokade** (izvršenje se odbija s jasnim razlogom):
   - korisnik je aktivan;
   - korisnik je vidljiv u AD-u kao aktivan;
   - SUPER_ADMIN, zadnji administrator ili servisni nalog;
   - pravna blokada;
   - otvoreni tiketi gdje je dodijeljeni agent (prvo ih treba preusmjeriti);
   - aktivni izvoz u toku.
3. **Pregled prije izvršenja** (dry-run): broj zapisa po tabeli i broj slobodnotekstualnih zamjena,
   uz primjer 3 zamjene s maskiranim kontekstom.
4. **Potvrda:** upis e-maila korisnika i ponovni MFA. Opcionalno „četiri oka”
   (`privacy.anonymization.requireSecondApprover`, zadano isključeno): drugi SUPER_ADMIN odobrava u
   roku od 7 dana.
5. Izvršenje je posao u workeru, u serijama, **idempotentno** (ponovno pokretanje nastavlja).
   Glavna tabela `User` se mijenja u jednoj transakciji, na kraju.
6. Rezultat: zapis `PrivacyErasure` i izvještaj (brojevi po tabeli, bez ličnih podataka),
   `privacy.subject.anonymized` u auditu, e-mail izvršiocu.

**Nepovratnost:** mapiranje „pseudonim → osoba” se **ne čuva**, pa se radi o anonimizaciji, a ne
pseudonimizaciji. Ostaje samo HMAC identifikatora (§6.4) koji sprječava ponovno vezivanje s AD-om.

### 6.3 Zamjena u slobodnom tekstu
- Traže se **tačni** nizovi: puni `displayName` (i varijanta „Prezime Ime”), e-mail, lokalni dio
  e-maila ako ima ≥ 5 znakova, `sAMAccountName`, broj telefona iz AD-a ako postoji. Poređenje ne
  razlikuje velika i mala slova, a za imena vodi računa o granicama riječi i dijakritici
  (Unicode NFC).
- Samo ime („Amra”) se ne mijenja, jer bi dalo previše lažnih pogodaka. Dokumentuje se kao
  poznato ograničenje.
- Obuhvat: tiketi gdje je subjekt podnosilac, učesnik, gost ili spomenut. Pretraga ide kroz
  indeksirane veze, ne kroz cijelu bazu.
- Svaka izmijenjena poruka dobija `redactedAt` (nova kolona). UI prikazuje diskretnu oznaku
  „dio sadržaja uklonjen zbog zaštite podataka”.

### 6.4 Sprječavanje „vaskrsavanja”
`PrivacyErasure` čuva `HMAC-SHA256(PRIVACY_TOMBSTONE_KEY, normalized email | objectGuid | entraOid)`.
AD/Entra sync i JIT provizioniranje provjeravaju ovu listu:
- ako se ista osoba ponovo pojavi aktivna (povratak na posao), kreira se **novi** korisnički nalog,
  uz upozorenje adminu, a stari anonimni se ne vraća;
- ako je u AD-u i dalje neaktivna, preskače se.

Ključ je u env-u i nije u bazi. Bez ključa se koristi izvedeni ključ iz `MFA_ENCRYPTION_KEY`
(dokumentovano).

### 6.5 Audit i hash lanac
Cilj: lanac ostaje provjerljiv i nakon anonimizacije i retencije.

1. **Hash v2 (za nove zapise).** Nova kolona `metadataDigest = SHA-256(canonical(metadata))` i
   `hashVersion = 2`. Hash v2 pokriva `metadataDigest` umjesto sirovog `metadata`. Metapodaci se
   tada mogu anonimizovati, digest ostaje isti, a lanac se **potpuno** verifikuje. Za redigovane
   zapise sadržaj se označava kao „redigovan” (`redactedAt`) i ne poredi se s digestom.
2. **Postojeći v1 zapisi** koji sadrže lične podatke u `metadata`: sadržaj se redigira, a zapis
   postaje **„zapečaćen”**. Verifikator provjerava vezu (`previousHash` → `hash`), ali ne i sadržaj.
   U isti lanac se dodaje zapis `audit.redacted` sa spiskom id-eva i njihovim originalnim hashovima,
   pa je vidljivo kada, ko i šta je redigovano. Rezultat verifikacije dobija
   `redactedCount`/`sealedCount`.
3. `actorUserId` i `entityId` ostaju, jer su tehnički id-evi, a osoba iza njih je anonimizovana u
   `User` redu. Prikaz u UI tako automatski postaje „Bivši korisnik #7F3A”.
4. **Minimizacija ubuduće:** audit zapisi koji danas upisuju e-mail (neuspjela prijava,
   Entra binder, reset MFA, rasporedi izvještaja) prelaze na `userId` gdje je poznat, a na
   **maskirani e-mail** (`a***@example.com`) i HMAC gdje nije (neuspjela prijava nepostojećeg naloga).
5. **Kontrolne tačke za retenciju audita** (§7): `AuditChainCheckpoint { throughId, throughCreatedAt,
   throughHash, purgedCount, createdAt }`. Verifikacija kreće od zadnje kontrolne tačke umjesto od
   genesis zapisa. Kontrolna tačka se upisuje i kao audit zapis `audit.retention.purged`.

### 6.6 Implementacijske odluke (korak 4)
Kod: `backend/src/modules/privacy/anonymization/`.

- **Identifikatori za zamjenu (§6.3).** Aplikacija ne čuva `sAMAccountName` ni telefon iz AD-a,
  pa se oni ne mogu tražiti. Traže se:
  - `displayName` i obrnuti redoslijed. Samo ako ima razmak ili ≥ 6 znakova, inače je to samo ime.
  - E-mail i njegov lokalni dio (≥ 5 znakova).
  - `distinguishedName`.
  - Login iz ručnog imenika (`ManualDirectoryUser.login`, veza po e-mailu), i kao `DOMENA\login`.
  - Granice su Unicode (`\p{L}\p{N}`), a tačka na kraju rečenice je dozvoljena.
  - Duži uzorci imaju prednost (e-mail prije lokalnog dijela).
- **Pseudonim.** `Bivši korisnik #XXXX` je nasumičan. Nije izveden iz id-a, pa nema nikakve veze s
  osobom. Dodjeljuje se pri zahtjevu i provjerava da nije već korišten (nakon 3 kolizije 6 hex
  znakova). Pregled prije zahtjeva koristi privremenu oznaku `#····`. I18n prikaz („Former user")
  dolazi s frontendom (korak 6), a u bazi ostaje bosanski oblik.
- **Obuhvat tiketa.** Tiket je u obuhvatu ako je osoba na njemu:
  - podnosilac, učesnik (i gost), autor poruke ili spomenuta;
  - autor priloga, odobravalac ili je na tiketu imala evidenciju vremena.

  Tiketi pod pravnom blokadom se **preskaču** (sadržaj ostaje), a njihov broj ulazi u izvještaj.
  `User` red se ipak anonimizuje. Ako to nije željeno, blokada se stavlja na korisnika, pa
  anonimizacija biva odbijena.
- **Scrub po tiketima:**
  - `title`, `description`, `formData`, `resolutionNote`;
  - poruke (uz `redactedAt`);
  - razlog prosljeđivanja;
  - bilješke i razlozi u evidenciji vremena;
  - komentar odobrenja i CSAT komentar;
  - `TicketActivity.payload`;
  - notifikacije drugih o tim tiketima, i lične i grupne.
- **Brisanje:**
  - notifikacije i potvrde čitanja osobe, e-mail isporuke, digest stavke, postavke i raspored
    obavještenja;
  - sesije, MFA, recovery kodovi, historija lozinki;
  - uloge, grupe, sačuvani pogledi, lični šabloni, veze FOLLOWER/WATCHER, dozvole za
    povjerljive tikete;
  - primalac izvještaja (raspored bez primalaca se pauzira, `enabled = false`);
  - `ManualDirectoryUser` s istim e-mailom;
  - kod ulaznih e-mailova: `fromAddress`, sirovi `.eml` i scrub naslova.

  `ChangeLog` (diff i razlog) se čisti gdje je osoba entitet ili akter. Podređenima se
  `managerUserId` postavlja na `null`.
- **Blokade.** „Aktivan u AD-u" znači da je nalog vezan za AD (`directoryObjectGuid`), a nije ga
  deaktivirao sync (`directoryDeactivatedAt` je `null`), nego samo admin u aplikaciji. Takav nalog bi
  sync ponovo kreirao. Uz blokade iz §6.1 dodane su i „već anonimizovan", „anonimizacija u toku" i
  „vlastiti nalog". Servisni nalozi nisu posebno modelovani, pa ih pokriva blokada SUPER_ADMIN/ADMIN.
- **Tok.** Zahtjev redom provjerava:
  1. blokade;
  2. ključ za tombstone (bez njega se zahtjev odbija s razlogom `tombstone_key_missing`);
  3. ručno upisan e-mail;
  4. MFA ili svježu sesiju.

  Zatim se sprema pregled i kreira se `PrivacyErasure`. Dvostruki klik ili dva admina serijalizuju
  se preko `SELECT … FOR UPDATE` na `User` redu. Posao `anonymize-user` ima jobId
  `anonymize-user-<id>`.

  Odobrenje („četiri oka") daje drugi SUPER_ADMIN, uz ponovnu provjeru blokada i MFA. Otkazivanje je
  moguće dok zahtjev čeka odobrenje ili je u redu.

  Održavanje (svakih 15 min):
  - ističe odobrenja starija od 7 dana (`approval_expired`);
  - nastavlja zaboravljene poslove u statusu QUEUED (> 5 min);
  - preuzima zastarjele poslove u statusu RUNNING (> 30 min).
- **Izvršenje** je idempotentno. Ponovni scrub nema pogodaka, a obrisano je već obrisano. Prije
  izvršenja blokade se provjeravaju ponovo: ako se osoba u međuvremenu aktivirala, status je
  `FAILED` s razlogom `blocked:…`.

  Zadnji korak je jedna transakcija. Ona obuhvata `User` (pseudonim, `anon-…@anonymized.invalid`,
  `null` polja, `authzVersion++`), tombstone vrijednosti, status COMPLETED i audit zapis
  `privacy.subject.anonymized`.
- **Audit.** Redigiraju se redovi gdje je osoba akter, gdje je entitet osoba ili tiket iz obuhvata,
  ili gdje metapodaci sadrže njen e-mail. Za v2 zapise lanac se i dalje potpuno verifikuje, što
  potvrđuje integracijski test. Zapis `audit.redacted` sadrži id, hash i verziju za najviše 2000
  redova. Audit zapisi zahtjeva, odobrenja i otkazivanja ne sadrže ime ni e-mail.
- **Povratnik (§6.4).** Tombstone je `HMAC-SHA256` nad `email:`, `guid:` i `oid:` (malim slovima).
  Ključ je `PRIVACY_TOMBSTONE_KEY` (≥ 16 znakova), a ako ga nema, izvodi se iz `MFA_ENCRYPTION_KEY`.
  - AD sync kreira novi nalog i u planu javlja izuzetak `RETURNING_ANONYMIZED`.
  - Entra JIT kreira novi nalog i u auditu `user.entra_jit_provisioned` dodaje
    `returningAnonymized: "true"`.
- **Premješteno u korak 6:**
  - e-mail izvršiocu po završetku;
  - obavještenje vlasniku pauziranog rasporeda;
  - UI oznaka „dio sadržaja uklonjen".
- **Retencija (ispravka koraka 3).** Arhivirani tiketi (`ARCHIVED`, nastaju iz CLOSED) ulaze u
  retenciju sadržaja.

- Noćni posao `privacy-retention` u 02:30 Europe/Sarajevo (worker, BullMQ repeatable, zaključavanje

### 7.5 Implementacijske odluke (korak 3)
- **Noćni prozor:** posao se provjerava svakih 15 min (minute 12/27/42/57) i pokreće jednom po lokalnoj noći
  u prozoru `[runAt, runAt + 3 h)`. Worker koji je bio ugašen u 02:30 nadoknađuje do 05:30, nikad
  preko dana. Jedno pokretanje po noći osigurava Redis ključ `privacy:retention:night:<datum>` (NX, 36 h).
- **Zaključavanje po kategoriji:** Redis `privacy:retention:lock:<kategorija>` (NX, 30 min). Noćni i ručni
  run se ne preklapaju; zaostali RUNNING red stariji od 30 min se označava FAILED (`stale`).
- **Kapija (§7.3):** prilozi, sadržaj i audit izvršavaju se samo uz uspješan dry-run iste kategorije
  s istim brojem dana (≤ 24 h) ili raniji EXECUTE s istim brojem dana. Inače run dobija status
  `SKIPPED` (`dry_run_required`). Promjena broja dana uvijek traži novi dry-run. Sesije, isporuke
  e-maila i registar zahtjeva ne traže dry-run (tehnički podaci, zadano uključeni).
- **Legal hold** štiti tiket i sve tikete podnosioca koji je pod blokadom.
- **Sadržaj tiketa:** naslov, opis, poruke i razlog prosljeđivanja dobijaju oznaku `[redacted]`
  (UI prikazuje prevedenu oznaku po `contentRedactedAt`/`redactedAt`). Brišu se: podaci forme,
  napomena rješenja, komentari CSAT-a i odobrenja, bilješke evidencije vremena, spominjanja i
  payload aktivnosti. Ostaje kostur: datumi, status, servis, OJ, SLA, CSAT ocjena. Naslov se
  redigira jer često sadrži ime osobe.
- **Prilozi:** fajl pa red; tiket se označava `attachmentsPurgedAt` tek kad su uklonjeni svi fajlovi
  (neuspjeh → sljedeći run, status PARTIAL).
- **Audit:** serije od 2000 najstarijih zapisa (prefiks lanca po `createdAt, id`) pod istim
  advisory lockom kao upis; svaka serija upisuje kontrolnu tačku i zapis `audit.retention.purged`.
- **Ručno pokretanje** (`POST /privacy/retention/:kategorija/run-now`) služi i kao test hook za E2E;
  kapija i dalje važi. Dry-run i ručni run izvršava worker (API samo stavlja posao u red, jedan
  po kategoriji i načinu).
- **Sedmični e-mail sažetak** retencije prebačen je u korak 6 (uz ostala obavještenja i UI).
- `RetentionRun` redovi se čuvaju 400 dana; CSV brojeva tiketa: `GET /privacy/retention/runs/:id/refs.csv`.
