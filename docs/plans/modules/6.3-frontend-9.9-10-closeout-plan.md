## 5. Faza 1 — FA1: stvarni cross-layer API contract fixtures

### 5.1. Problem

Ticket incident je pokazao dvije vrste drifta:

- frontend parser je očekivao `number`, dok je stvarni DTO koristio `ticketNumber`;
- backend list service je izračunavao `totalsAsOf`, frontend ga je zahtijevao, ali završni response mapper ga nije slao.

Minimalni ručno napisani frontend fixture nije predstavljao stvarni backend response i zato nije otkrio kvar.

### 5.2. Ciljna arhitektura

Uvesti neutralni contract-fixture sloj koji može koristiti i backend i frontend test bez runtime zavisnosti jednog paketa od drugog.

Preporučena lokacija:

- `contracts/fixtures/*.json` za čisti JSON;
- `contracts/fixtures/*.ts` samo ako je potreban builder bez Node/backend importa;
- schema/version metapodatak uz svaki fixture;
- frontend parser test čita isti fixture;
- backend response-mapper test proizvodi ili poredi isti javni oblik.

Fixture nije snapshot cijelog internog Prisma modela. Sadrži stvarni javni response envelope i reprezentativne permission-sensitive varijante.

### 5.3. Prioritetni ugovori

#### 5.3.1. Tickets

- paginated list sa 0 i više redova;
- `totalIsCapped` prisutan/odsutan;
- `totalsAsOf` prisutan;
- confidential/permission-sensitive projekcija;
- group inbox;
- ticket detail minimalni i puni response.

#### 5.3.2. Session/Auth

- current session USER/AGENT/scoped admin/SUPER_ADMIN;
- login success;
- MFA required;
- enrollment required;
- must-change-password;
- nullable OU polja.

#### 5.3.3. Services/Status

- service list i aktivna form summary projekcija;
- availability/status incident;
- downtime/upcoming count;
- addon-disabled oblik gdje je primjenjivo.

#### 5.3.4. Routing/Settings/Users

- paginated routing coverage;
- permission-sensitive settings registry;
- user summary list;
- config package preview/import report.

### 5.4. Negativni ugovori

Svaki parser mora dokazati:

- pogrešan envelope tip se odbija;
- pogrešan obavezni scalar se odbija;
- optional/permission-sensitive polje ne ruši cijelu listu ako ugovor dozvoljava odsustvo;
- request ID ostaje vezan za `INVALID_API_RESPONSE`;
- malformed JSON daje kontrolisanu grešku.

### 5.5. Anti-drift guard

Dodati test koji enumerira sve `apiRequestValidated` pozive i provjerava da critical boundary katalog ima:

- parser;
- pozitivni fixture;
- negativni test;
- owner/domain oznaku.

Ne uvoditi runtime JSON-schema biblioteku bez jasne bundle analize. Cilj je dokaz ugovora, ne automatsko povećanje client bundlea.

### 5.6. Acceptance

- ticket response mapper i frontend parser dijele isti fixture;
- bug klase `ticketNumber/number` i izostavljeni `totalsAsOf` više ne mogu proći test;
- svi critical parseri imaju reprezentativan neprazan fixture;
- frontend i relevantni backend testovi zeleni.

### 5.7. Commit grupa

- `test(contracts): share critical api response fixtures`
- `test(frontend): enforce validated boundary fixtures`

**Status implementacije (22.10.2026.): završeno.** Zajednički `contracts/fixtures/critical-api-responses.json` pokriva svih osam critical boundary kategorija i MFA međustanje. Frontend boundary registry sada zahtijeva parser, shared fixture i owner; parser suite koristi stvarne neprazne odgovore i negativno zaključava stari `number` alias. Backend ticket responder koristi čisti envelope mapper koji se testira istim fixtureom, uključujući `ticketNumber` i `totalsAsOf`. Frontend ciljni suite prolazi **3/3 fajla i 25/25 testova**, ESLint i production build prolaze; backend ESLint i ciljani Jest prolaze **1/1 suite, 2/2 testa**. FA1 je zatvoren.

## 10. Faza 6 — FA4: profiler i performance dokaz

### 10.1. Cilj

Razdvojiti dva legitimna performance dokaza:

1. produkcijski browser long tasks i route load behavior;
2. React commit duration/rerender count iz profiling-enabled React builda.

### 10.2. Produkcijski gate

Zadržati:

- `?profile=1` opt-in;
- long-task observer;
- unaprijed deklarisane pragove;
- JSON artefakt;
- dashboard, ticket list/inbox/detail, assets veliki dataset i catalog veliki skup.

Production test ne smije tvrditi da je izmjerio React commit ako production React callback nije dostupan.

### 10.3. Profiling-enabled build

Istražiti i implementirati zaseban build mode samo za CI/performance:

- React profiling bundle;
- nije default production artefakt;
- ista aplikacijska konfiguracija i minifikacija gdje je moguća;
- eksplicitna oznaka u artefaktu `buildKind: react-profiling`;
- commit/rerender pragovi;
- cold i warm navigacija odvojeno;
- fixture veličina zapisana uz rezultat.

Ako React/Vite verzija ne omogućava pouzdan profil build bez mijenjanja runtime semantike, izuzetak ostaje formalno prihvaćen uz:

- tehnički dokaz;
- ownera;
- datum revizije;
- production long-task gate;
- maksimalnu performance ocjenu ispod 10.

### 10.4. Pragovi

Prije optimizacije zaključati:

- maksimalan broj commitova po scenariju;
- maksimalni pojedinačni commit;
- ukupno commit trajanje;
- maksimalni broj long taskova;
- ukupno long-task trajanje;
- fixture cardinality;
- browser i hardware/runner klasu.

### 10.5. Acceptance

Za 10/10:

- stvarni profiling build daje >0 React commitova;
- svi pragovi zeleni ili svaki izuzetak ima owner/rok;
- production bundle nema profiling overhead.

Za 9,9:

- production long-task gate zelen;
- React limitation formalno prihvaćen i periodično revidiran;
- nema lažne tvrdnje o commit mjerenju.
