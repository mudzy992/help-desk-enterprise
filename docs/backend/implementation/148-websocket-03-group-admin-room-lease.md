## Nalaz i acceptance

Izvorni audit je našao petominutni prozor prije group/admin room revalidationa i fail-open ponašanje kada DB membership read ne uspije. Cilj je da podržana group/RBAC promjena invalidira postojeće sockets na svim instancama, da se stari authz lease ne može obnoviti, te da nedostupan autoritativni membership read ne ostavi socket u nesigurnim managed sobama.

Zatvara se samo `BA-websocket-03`. `BA-websocket-14` i njegova šira revocation/cross-instance/E2E acceptance matrica ostaju otvoreni.

## Implementacija

- `SocketGroupMembershipService.roomAccessForUser()` vraća jednim joined Prisma snapshotom `isActive`, `authzVersion`, group ID-eve i ADMIN/SUPER_ADMIN assignment. Room grants zato odgovaraju istom durable authz versionu kao socket lease.
- Initial group/admin room join i periodična revalidation koriste istu snapshot putanju. Ako korisnik nedostaje, nije aktivan ili je DB `authzVersion` drugačiji od leasea, socket se disconnecta; ne pokušava se in-place grant starom leaseu.
- Group/admin reconciliation radi svakih **30 sekundi**, odmah pri startu, bez preklapanja sweepova. Sockets se grupišu po korisniku, pa se isti snapshot čita jednom za više browser tabova; concurrency je ograničen na 25 korisnika po procesu, a autoritativni read timeout je 5 sekundi.
- Ako snapshot read ne uspije ili istekne, uklanjaju se sve managed `group:*` i `role:admins` sobe za tog korisnika. `user:*` i ticket sobe ostaju u vlasništvu njihovih zasebnih kontrola. Ako `leave` ili partial join/leave ostavi room stanje neizvjesnim, socket se disconnecta. Neuspjeh emituje alertabilni structured warning `socket_room_revalidation_failed ... fail_closed=1`.
- Group member add/remove/delete i podržane user/role authz mutacije pozivaju postojeći `PrincipalContextInvalidator` nakon DB commita. On bumpa `User.authzVersion` i best-effort emituje `users` invalidation na `servicedesk:auth:socket:invalidate`; svaki API proces disconnecta podudarne lokalne sockets. Već postojeći 15-sekundni session lease read je durable fallback i fail-closed je na DB/cache grešku ili authz-version drift. 30-sekundni room sweep ostaje reconciliation fallback za propuštene/out-of-band promjene, ne primarni mutation revocation put.

## DB load procjena reconciliation sweepova

- Room sweep: jedna joined SQL query po različitom validnom/authenticated subject-u u lokalnoj Socket.IO mapi na 30 sekundi. Za instancu `i` sa `U_i` distinct subject-a, code-derived steady-state je `ΣU_i / 30` SQL statements/s; 1.000 subjects na jednoj instanci ≈ **33,3 SQL reads/s**. Više tabova istog korisnika share-a isti read.
- Odvojeni session-lease safety sweep svakih 15 sekundi radi jedan durable SQL read po različitoj neistekloj lease grupi (`L_i`; različiti tokeni istog korisnika mogu se brojati odvojeno). `sid` putanja je joined session/user read; legacy token direktno čita user. Jedan Redis MGET se šalje po lease-u kada je Redis konfigurisan. `L_i/15` je dodatni SQL reads/s; 1.000 subjects + 1.000 jedinstvenih lease-eva daje oko **100 SQL reads/s** zbirno na jednoj instanci, plus oko 66,7 Redis MGET/s.
- Oba scheduler-a pokreću sweep odmah pri startu, pa ove formule su dugoročni steady-state prosjek; ne uključuju početni burst do `U_i` room reads i `L_i` lease reads po instanci. Istovremeni restarti više instanci mogu poravnati te burstove; runtime jitter/trace nije izmjeren.
- Oba imaju concurrency cap 25, 5s caller timeout i per-process non-overlap guard. Timeout je `Promise.race`, ne DB statement cancellation; zato tokom zastoja in-flight SQL može prerasti cap i timeoutovani upiti se mogu akumulirati iako wrapper sweep nije overlapped. Ovo su procjene iz koda, ne runtime query trace ili load test; nisu uključeni normalni API upiti.
