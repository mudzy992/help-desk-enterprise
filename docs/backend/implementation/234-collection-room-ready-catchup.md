# WR-01 — liste/dashboard: catch-up nakon pridruživanja sobama

**Status: implementirano, lokalno testirano; browser acceptance i Redis cross-instance ostaju otvoreni.** Paket [228](228-websocket-follow-up-plan.md).

Socket `connect` potvrđuje transport, ne završetak async autorizacije i pridruživanja user/group sobama. Ako se REST snapshot dovrši prije pridruživanja, promjena u međuvremenu može biti propuštena. Dva deterministička frontend hook testa prije izmjene pokazala su da kasno završavanje soba ne aktivira drugi catch-up i da se takav catch-up ne čuva dok je tab skriven. To je dokaz nedostajuće klijentske reakcije na predloženi signal, ne samostalni dokaz produkcijskog racea.

Nakon uspješnog user-room join-a i autorizovanog group/admin room reconciliationa gateway emituje samo tom socketu sadržajno prazan `socket.rooms.ready`; ne emituje ga kad setup nije uspio ili je socket odspojen. Hook liste/dashboarda na njega invalidira in-flight lokalne snapshot generacije i zakazuje debounced REST reload; `connect` fallback ostaje radi kompatibilnosti sa starijim serverom. Brzi `connect`/ready spajaju se u jedan reload; skriveni tab čeka povratak. Dodatni hook test potvrđuje da stari list snapshot ne prepisuje noviji, uz raniji ekvivalent za dashboard i stvarni React Query cancellation test.

Lokalno je prošlo 25 ciljnih frontend testova, TypeScript i ciljani ESLint frontend/backend. Server gateway test proširen je da provjeri da ready ne prethodi sporom join-u i da ne postoji nakon neuspjeha room setupa; lokalno nije mogao biti izvršen jer `prisma generate` ne može preuzeti engine zbog mrežnog/TLS ograničenja, pa generated-Prisma i gateway dokaz mora doći iz CI. Ovo nije dugotrajni replay, potvrda zdravlja Redis adaptera ni garancija da kasniji periodični oporavak nakon neuspjelog setupa emituje ready. Event se može izgubiti i u slučaju starije backend verzije ili neisporučivog socketa; cross-instance degradacija bez reconnecta ostaje otvoren rizik. Nema migracije, novih permisija ili promjene članstva soba.

## Browser acceptance — po korisnikovom mergeu i redeployu

Koristiti dva testna računa, sa jasnim pravima i testnim tiketima; nema promjene permisija ni prekida produkcijskog Redis-a. A je globalni admin ili agent s pristupom testnim tiketima i član grupe kojoj se tiket rutira, B je drugi korisnik koji može kreirati tiket. Pri provjeri liste otvoriti **Tiketi → Svi tiketi**, **Pretraga** postaviti na jedinstveni naslov koji će B koristiti, bez drugih filtera; dok A ostaje na listi B kreira tiket. Očekuje se vidljiv red bez ručnog osvježavanja nakon obrade eventa; ako je tiket izvan A opsega, test nije primjenjiv. Isti postupak ponoviti nakon što A tab bude skriven dok B kreira drugi tiket, pa ga vratiti. Za reconnect na A u browser DevTools → Network izabrati Offline, B kreira treći tiket, A vratiti Online i posmatrati listu bez reload stranice. Test na **Nadzorna ploča** odvojeno: A ostaje na toj stranici, B kreira nov tiket u A opsegu; broj **Otvoreni tiketi** i/ili red u **Nedavni tiketi** / **Tiketi koji zahtijevaju vašu pažnju** treba odraziti promjenu, u skladu s filterima i rangiranjem; ponoviti hidden/reconnect. Ako nema izolovanog računa ili postoje paralelne promjene koje onemogućavaju pouzdano poređenje, označiti N/A, ne tvrditi izolovani dokaz. Za spor REST koristiti DevTools Network throttling samo testnog taba i ponoviti dok se request vraća; ako se tajming ne može pouzdano ostvariti, označiti N/A. Sačuvati status DA/NE/N/A, preglednik, commit deploya, cleanup i uočeno vrijeme; R1/R2 ostaju N/A bez potvrđene dvije instance/izolovanog Redis outage okruženja.
